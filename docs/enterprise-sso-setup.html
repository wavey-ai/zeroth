Implement and test both providers before supplying live credentials. Keep each provider disabled until its application registration, secret binding and live login checks are complete. Applications continue to trust Zeroth's issuer.

All domains and identifiers below are examples. This guide does not create cloud resources or claim that a production organization is connected. Customer-specific connection management and the application proxy are later work.

1. Configuration contract

Both providers use the exact callback https://id.example.com/oauth2/callback. Replace the example origin with the deployment's PUBLIC_BASE_URL.

Workspace credentials are separate from consumer Google login's GOOGLE_CLIENT_ID and GOOGLE_CLIENT_SECRET. Public client IDs may go in Wrangler variables. Secrets stay in managed secret bindings.

2. Microsoft Entra registration

  1. In the intended directory, open Entra ID → App registrations → New registration. Choose the single-tenant account type for this implementation and record the directory and application GUIDs. Microsoft registration guide.
  2. Add a Web platform with the exact callback. Zeroth requests openid profile email using the authorization-code flow and redeems the code on the server. An implicit-flow token response is not needed. Microsoft code-flow documentation.
  3. For this client-secret adapter, create a credential under Certificates & secrets. Put its value, rather than its secret ID, into ENTRA_CLIENT_SECRET and track expiry. Microsoft recommends certificates or federated credentials for production; those methods require separate adapter support. Microsoft credential guidance.
  4. Use enterprise-app assignment to control admitted users and guests. The adapter pins the tenant and issuer. Email and preferred_username are optional profile data, not tenant-membership proof. Microsoft claim semantics.

3. Google Workspace registration

  1. In the selected Google Cloud project, configure OAuth branding and audience. Create a Web application OAuth client and add the exact callback to its authorized redirect URIs. Use its client ID and secret for the Workspace bindings. Google OIDC setup.
  2. Set GOOGLE_WORKSPACE_DOMAINS to the exact managed domains to admit. Add secondary domains explicitly. Do not enter URLs, email addresses or wildcards.
  3. Require the signed token's hd claim to match. The authorization request's hd parameter only guides account selection; an email suffix alone does not prove Workspace membership. Reject consumer accounts and unexpected hosted domains. Google hosted-domain validation.

4. Prepare configuration before credentials

From crates/zeroth-worker, run npm run test:config. These fixture tests need no cloud account. Once real public identifiers are available, use these installer options or the matching environment variables:

node scripts/install-config.mjs \
  --auth-origin https://id.example.com \
  --d1-id YOUR_D1_DATABASE_UUID \
  --entra-tenant-id YOUR_DIRECTORY_GUID \
  --entra-client-id YOUR_APPLICATION_GUID \
  --google-workspace-client-id YOUR_WEB_CLIENT_ID.apps.googleusercontent.com \
  --google-workspace-domains example.com,subsidiary.example \
  --disabled-providers entra,google_workspace \
  --out wrangler.generated.jsonc

This creates a complete deployment configuration. Preserve the existing deployment's other installer options and provider-disable settings. The installer validates public settings and never copies secrets from the environment into the file.

After credentials exist, supply secrets for the selected target:

npx wrangler secret put ENTRA_CLIENT_SECRET --config wrangler.generated.jsonc
npx wrangler secret put GOOGLE_WORKSPACE_CLIENT_SECRET --config wrangler.generated.jsonc

For a local presence check, inject bindings into the process environment from your secret manager and run:

node scripts/check-enterprise-config.mjs --provider all --auth-origin https://id.example.com

The preflight reports binding names, presence and validation errors. It does not print credentials, contact providers, inspect managed cloud secrets or verify login. Remove a provider from DISABLED_PROVIDERS when ready to enable it in the selected deployment.

5. Require enterprise sign-in for an application

In the client editor, choose Required enterprise sign-in → Microsoft Entra or Google Workspace. The API field is enterpriseProvider: entra, google_workspace or an empty value to clear it. Client updates replace the resource; preserve this field on every edit.

6. Acceptance and recommendations

  1. Complete implementation checks first. Run workspace tests, the Worker wasm check, UI checks and configuration tests with fixture identities.
  2. Connect test organizations later. Exercise valid login, incorrect tenant/domain, personal accounts, guest assignment, nonce mismatch, wrong audience and key rotation. Another login method must not satisfy an enterprise-required client.
  3. Exercise session policy. Check codes, refresh tokens and silent SSO against the required provider and current configuration. A policy edit must not reopen access through an older session.
  4. Build the application proxy last. Use the project's own web0services crates once enterprise-policy tests pass. Forwarding, product-local sessions and private-upstream enforcement are a separate implementation.

OIDC login is not provisioning or immediate offboarding. Session revocation and access-token expiry define the current access window. Directory synchronization and richer connection lifecycle controls need separate work.
