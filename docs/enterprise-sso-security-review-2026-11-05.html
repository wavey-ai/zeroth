2. Security review and fixes

Priority / attack pathConfirmed failure and correction
Critical — password signupWith password auto-signup enabled, a caller could attach a new password to an existing account by supplying its email. Signup now refuses existing accounts; authenticated password changes require the account CSRF token.
High — silent SSOA session from an unrestricted app could receive a code for an app in another namespace or with a restricted email domain. Both session-reuse paths now check the destination policy. Code redemption and refresh issuance recheck current admission.
High — fabricated mailbox proofPassword signup accepted a claimed corporate address; passkey registration set the email verification flag without mailbox proof. Restricted clients now require trusted stored verification. Legacy passkey flags no longer satisfy email-domain or email-based admin admission.
High — local credential isolationGlobally keyed local credentials were usable with tenant/client account settings. Password, magic-link and passkey flows now reject non-global clients at initiation and completion. Wallet completion checks the current namespace and domain policy.
High — account deletionAn ordinary OAuth access token with profile access could delete the whole user account. Deletion now requires the hosted account session and its CSRF token.
High — refresh replay raceReplay revocation could run between parent rotation and child insertion, leaving a new active token after family revocation. Replacement insertion now atomically requires an unrevoked parent. User-wide revocation also tombstones rotated parents.
High — gate audience confusionA valid credential for another Zeroth client could open the static gate. The gate now requires a configured application client ID and an exact match in the validation response.
High — protected response cachingOrigin asset responses could retain public/shared cache directives after authentication. The gate now applies private caching or no-store and removes CDN/surrogate cache overrides.
Medium — return URL reinterpretationA same-origin absolute URL with a double-slash path could become an external authority when rejoined. The web-auth helper now rejects ambiguous paths and validates fallback targets.
Medium — failed random sourceThe web-auth helper generated predictable timestamp-derived state and PKCE values when secure randomness failed. It now fails closed. State MAC verification also uses the library's constant-time verification API.

An existing AWS authorizer test also had a wall-clock boundary race. Its clock is now fixed during the test; the production expiry and issue-time checks retain their behavior.

Native Spotify exchange now fails closed. Fetching a profile with a Spotify access token did not establish which upstream client received that token. A caller-supplied allowed client ID did not fix that. Hosted Spotify authorization-code login remains supported; native clients must use that flow.

Dependency updates: the lockfile now includes patched TLS, certificate-verification, root-store, event-listener and Tokio versions. P-256 and K-256 were upgraded to 0.14, resolving crypto-bigint to 0.7.10. Frozen signatures from the previous versions check ES256 verification and EVM recovery compatibility. The crypto arithmetic advisory concerns timing leakage whose practical exploitability depends on the operation, compiler and target; this review did not demonstrate signing-key recovery. RUSTSEC-2026-0387.

Self-requested permission scopes now fail closed. A caller could request a scope such as api:write, receive it in a signed token and satisfy a downstream scope check without a grant decision. The issuer now accepts only openid, profile, email and offline_access. Requests and stored grants with custom scopes are rejected; application permissions need an explicit grant model.

Mailbox preclaims and passkey bootstrap: an attacker could register an unverified password account with the victim's email. A later magic link or admin passkey bootstrap could select that account by email and give it the victim's mailbox proof or admin membership. Magic links now select only a unique verified global mailbox owner; otherwise signup uses a fresh empty account and a separate canonical magic_link identity. Bootstrap passkeys use a fresh account; attaching a passkey to an existing account requires its matching authenticated session. Old unsafe pinned links and ambiguous owners are rejected.

Canonical identity evidence: a stale legacy identity row could retain a verified email after the canonical row changed. Local login, token claims and admin queries now suppress shadowed legacy rows. Regression tests exercise both downgrading and restoring canonical verification.

Compatibility changes: non-global local authentication and native Spotify exchange now fail closed; custom permission scopes cannot be minted or renewed. An unverified legacy account is not recovered by matching its email. New mailbox login may create a separate account, and ambiguous ownership requires explicit resolution. These restrictions are deliberate until namespaced local credentials, verified signup and grant policy are implemented.

The agents reviewed protocol and token handling; browser, local-auth and account management; and downstream gates and relying-party helpers. Findings require a concrete attack path or demonstrable failure. Existing audit notes were treated as investigation leads. Regression tests exercise policy helpers, real SQL transitions or the gate request handler; a deployed Worker/D1 adversarial exercise remains a separate validation step.

3. Enterprise connections and the trust boundary

Applications should continue trusting Zeroth's issuer and keys. Zeroth should broker upstream enterprise login and enforce which organization and connection can access each application. A login provider button or an email-domain filter alone cannot enforce this.

Introduce a connection record containing an opaque connection ID, organization ID, provider kind, upstream client ID, secret-binding reference, allowed issuer, tenant or hosted-domain restrictions, enabled state and configuration revision. Keep secrets in deployment secret storage. Start with admin-managed, provider-specific connection configuration; postpone arbitrary discovery URLs until outbound URL validation and SSRF controls exist.

ObjectRequired binding
Application policyAllowed connection IDs and organization; whether enterprise login is mandatory; admission rules and session lifetime.
Upstream transactionConnection ID and revision, organization, downstream client, redirect URI, browser state, fresh upstream nonce and upstream PKCE verifier. Resolve the connection from stored state on callback.
IdentityUnique by account namespace, connection ID, exact upstream issuer and stable subject. Preserve existing social identities through an explicit migration. Never merge by email.
Session and grantsOrganization, connection and authentication provenance. Preserve them through authorization codes and refresh rotation. A social or password session must not silently satisfy an enterprise-required application.
Membership and rolesExplicit organization membership and application role mapping. Zeroth's deployment-wide admin role must not automatically become a customer application's admin role.

Enforce this policy before issuing a browser session, authorization code, native-exchange token or refreshed token. Recheck it during silent SSO and account linking. Reject a disabled connection or incompatible session, and require a fresh enterprise login where appropriate. Disabling a connection should revoke its Zeroth sessions and refresh tokens. Locally validated access tokens remain usable until expiry unless the application makes an online revocation check.

Until local authentication is isolated and its policy enforced consistently, enterprise-required applications should reject password, magic-link, passkey and wallet sessions that lack an approved enterprise authentication context. Verified email ownership can be useful account data; it does not establish continuing employment or organization membership.

4. Microsoft Entra and Google Workspace

4.1 Microsoft Entra

Start with the Microsoft public cloud and a tenant-specific v2 OIDC authority for each connection. Pin the configured tenant GUID and exact issuer. Verify the ID-token signature, audience, nonce and validity window, plus agreement between tid, the expected tenant and issuer. Do not infer tenant membership from an email or preferred_username. For tenant-independent metadata, Microsoft also requires signing-key issuer validation. Microsoft issuer-validation requirements.

Use (connection, issuer, sub) as the OIDC identity key. Keep (tid, oid) as directory identity provenance when cross-application mapping is needed. Treat email and display names as optional, mutable profile data; do not manufacture email_verified=true. Decide whether invited guests are admitted, and use enterprise-app assignment or explicit membership for admission. Group overage requires a deliberate Graph lookup or denial policy. Microsoft claims reference.

Setup requires a Web app registration, the exact Zeroth callback URI, client credentials, openid profile email scopes and a test user in the selected tenant. OIDC sign-in does not require reading Microsoft Graph. Leave directory sync, group enrichment and sovereign-cloud authorities for later explicit support. Microsoft OIDC endpoints and flow.

4.2 Google Workspace

Reuse the existing Google OIDC adapter, adding a Workspace connection policy. Require the signed hd claim to match an exact configured hosted-domain allowlist after normal issuer, signature, audience, expiry and nonce validation. Reject a missing or unexpected hd. The authorization-request hd parameter is a selection hint; enforce the claim returned in the token. An email ending in the company's domain is insufficient. Google OIDC hosted-domain guidance.

Use Google's stable sub for identity, and retain verified email separately. Support additional Workspace domains by explicit configuration and tests. Consumer Google login can remain available for social applications while enterprise-required applications accept only approved Workspace connections. Google ID-token validation guidance.

Neither provider's login flow is a provisioning or immediate offboarding mechanism. Define a maximum session age and a short access-token lifetime. Add explicit organization suspension and revocation before claiming reliable offboarding. SCIM, directory synchronization, SAML and customer group-to-role mapping are separate capabilities.

5. An OAuth2 Proxy style application proxy

The implementation order is Entra and Google Workspace first, then our own proxy built with the web0services crates. The proxy will be a downstream Zeroth OIDC client. Its runtime and deployment adapters will be selected after checking the crates; this document does not claim that integration is implemented.

5.1 A native Zeroth proxy

If a Worker proxy is needed, add a separate deployable adapter using the existing zeroth-oidc verification and path-policy helpers. Its first version should support one configured upstream or service binding, a fixed public origin, login/callback/logout endpoints, opaque product-local sessions, renewal and an authorization-only endpoint. Use fixed upstream configuration, never a caller-supplied target URL.

Forward bodies and methods without silently replaying unauthenticated mutations after login. Return 401 for API authentication failures and 403 for authenticated policy failures; redirect only browser navigations. Strip spoofed identity and forwarding headers, limit trusted ingress hops, suppress caching of protected responses, bound body size and timeouts, and define streaming and WebSocket behavior. Keep the application origin private. Use one canonical path interpretation for authorization and forwarding.

A Rust container adapter can share the pure policy crate but needs its own HTTP server, streaming transport and session store. Cloudflare service bindings and native network transports should stay in their adapters. Measure Worker CPU and D1 usage; the repository's free-tier latency target is not a result measured by this investigation.

6. Recommended delivery sequence

  1. Land and validate the security fixes. Run native tests, the wasm check and the gate tests on the combined main branch. Record dependency advisories that remain and exercise the affected flows in a disposable Worker/D1 deployment.
  2. Add connection policy and authentication provenance. Implement schema, admin configuration, application allowlists, transaction binding and session/grant enforcement before enabling enterprise-required access. Test cross-organization login, linking, refresh and silent SSO denial.
  3. Add Entra and Workspace together behind disabled connections. Implement tenant-specific Entra OIDC and signed Google hosted-domain policy. Exercise wrong tenant/domain, personal accounts, guests, wrong audience, expired credentials, nonce mismatch and key rotation using dedicated test organizations.
  4. Build our proxy last, using web0services. Reuse the verified Zeroth protocol and policy helpers; add end-to-end tests covering forwarding, sessions, parallel renewal, header trust, streaming, private upstreams and failure behavior. Keep platform adapters separate from the shared policy.
