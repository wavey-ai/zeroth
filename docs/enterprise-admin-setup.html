WAVEY / ZEROTH · SETUP GUIDE

Corporate sign-in, provisioning & audit delivery

Microsoft Entra SCIM, Google Workspace Directory sync and independent audit adapters.

5 November 2026 · Author: Codex · Ticket: no issue linked

Create a tenant, bind its applications, configure corporate sign-in and activate directory-driven access. Offboarding revokes local sessions and refresh credentials when its update is applied. Audit capture stays local and durable; external destinations are optional.

This guide describes implementation and operator configuration. A saved draft or configured credential is not evidence of a successful live sign-in. Provider credentials can be supplied after the tenant is created.

01 / Tenant setup

  1. Open Tenants in the management UI using a deployment-admin session.
  2. Choose a stable tenant ID and a display name. Select Microsoft Entra or Google Workspace. The initial model has one corporate connection per tenant.
  3. Select existing applications. Binding sets their tenant account namespace and required enterprise provider. Ownership is permanent in this implementation; disable an application instead of moving it between companies.
  4. Add audit readers by their Zeroth user ID. Export permission is separate from read permission. Readers do not gain deployment-admin or user-management rights.
  5. Save the draft. Supply the public provider application ID and credential binding when available. Test a fresh login before onboarding users.

Worker deployments resolve these references through secret bindings. The dedicated TENANT_…_CLIENT_SECRET namespace prevents references to unrelated signing or administrative credentials. A tenant connection never falls back to another tenant's or the deployment's credentials.

Decide whether Entra guest accounts are eligible and configure enterprise-app assignment accordingly. Workspace domain membership alone does not grant an application role. Apply corporate MFA/Conditional Access policy at the upstream provider; SSO alone does not prove MFA.

03 / Entra SCIM provisioning

A customer-owned Entra tenant and application are sufficient. This implementation uses each customer's own directory tenant GUID and OIDC application registration. The customer also configures its Entra enterprise application to push SCIM users to Zeroth. Wavey does not need an Entra tenant for this per-customer model. Wavey would need a home tenant if it later operated its own shared multi-tenant app registration. Microsoft's tenancy model.

  1. Save the Entra tenant in Zeroth first. In its provisioning section, copy the tenant-specific SCIM endpoint: ISSUER/scim/v2/TENANT_ID.
  2. An operator generates a separate random provisioning token and stores it in a dedicated deployment secret, such as TENANT_ACME_SCIM_TOKEN. Enter only this binding name in Zeroth. Supply the same token securely to the customer's Entra administrator; Zeroth never displays or stores its value in tenant metadata.
  3. In the customer's Entra enterprise application, configure automatic provisioning to the copied Tenant URL and supply the token in the Secret Token field. Use a non-gallery custom application if needed. Test the connection, choose the assigned users in scope, and start provisioning. Microsoft's SCIM integration instructions.
  4. Map the stable Entra objectId to SCIM externalId, userPrincipalName to userName, and lifecycle state to active. Zeroth binds provisioned membership to the signed OIDC object ID; email is not an account-attachment key. The initial implementation supports Users, not Groups or automatic group-to-role assignment.
  5. Turn on Require active provisioned users in Zeroth. This admission-policy change invalidates earlier tenant grants. Run initial provisioning before users sign in: an unknown identity is denied until an active provisioned member record exists.
  6. Deactivate a test user through Entra and verify a SCIM active=false update revokes local grants and prevents fresh sign-in. Reactivation must arrive as an explicit active directory record. Inactive tombstones are retained even if the provisioned-user requirement is later switched off. Switching it off permits unknown signed corporate identities; it does not pause SCIM delivery or restore an inactive member.

Credential presence is configuration evidence. Last SCIM activity reports requests received by Zeroth, not the health or completeness of Entra's entire provisioning job. Check Entra provisioning logs as well. Incremental provisioning is asynchronous and commonly runs every 20–40 minutes; initial provisioning can take longer. Microsoft's provisioning status guide.

04 / Google Workspace Directory sync

  1. Use a customer-owned Google Cloud project with the Admin SDK Directory API enabled. Create a service account and authorize domain-wide delegation in Google Admin using its numeric client ID and https://www.googleapis.com/auth/admin.directory.user.readonly. Google's service-account delegation guide.
  2. Choose an active, unarchived Workspace super-administrator account as the delegated admin. Zeroth verifies this privilege to avoid treating an administrator's restricted directory view as evidence that users were deleted. The granted OAuth scope remains read-only; sync does not write the Google directory.
  3. Store the complete service-account JSON key only in a dedicated deployment secret, such as TENANT_ACME_GOOGLE_DIRECTORY_SERVICE_ACCOUNT. Save its binding name, delegated super-admin email and exact Workspace customer ID in the tenant's Directory settings. Do not use the my_customer alias or a domain as the customer ID. A verified directory ID becomes locked; a different directory requires explicit migration.
  4. Enable automatic directory polling, then run Sync directory now. Managed access becomes enforced after activation and existing grants are invalidated. Verify the last complete successful sync and member counts before onboarding users. The target polling interval is 300 seconds. The Worker template and generated configuration include a five-minute Cron Trigger; deploy that configuration and confirm scheduled invocations are running.
  5. Test suspended, archived and deleted members. Zeroth reads all pages for the pinned customer and uses immutable directory IDs. Missing previously managed principals require confirmation before deactivation. Incomplete, wrong-customer or failed snapshots do not bulk-deactivate members. Google's API separates paginated current/deleted listings. Directory users.list reference.

Pausing polling does not disable managed-access enforcement. If no complete successful scan refreshes the directory for 900 seconds, new sign-ins and online grants are denied until a validated scan restores freshness. Failed scans preserve the last successful state; they do not report a false success. Verify delegation, key availability, customer ID and the fixed error code shown in the UI.

Directory polling has bounded requests and roster sizes; it is not a load-tested scale guarantee. Validate the Worker CPU and D1 plan limits against a representative customer directory before enabling production enforcement.

05 / Users, access and the offboarding window

The user-management UI supports inspection, tenant filtering, disable/enable and deployment-admin membership changes. Provisioning source counts describe directory membership; they are separate from the displayed local account inventory. There is no invitation workflow. SAML remains deferred.

When Zeroth applies an inactive directory record, it revokes that member's local tenant sessions and refresh credentials. Manual user disable also revokes local grants. Corporate browser sessions also expire eight hours after their original authentication time, including sessions reused for silent SSO. New enterprise access tokens are capped at 300 seconds; an offline consumer can accept an already issued JWT until its expiry. Overall offboarding delay includes Entra delivery or Google polling, upstream propagation and any outstanding JWT lifetime. Do not promise immediate revocation at the moment an upstream administrator changes a user.

Tenant bindings govern new identity lookup. Existing unassigned/global accounts are not silently migrated into a corporate tenant. Review account ownership before changing an application's namespace. Audit rows with unknown legacy ownership remain in the deployment operator's history.

06 / Audit history

Administrative writes and critical credential transitions capture an audit record and outbox entry in the database transaction. Audit history survives account deletion as opaque actor/target references. New records use bounded, allowlisted metadata and explicit outcomes; raw tokens, provider error descriptions and credentials do not belong in the event payload.

Deployment admins use the management audit table or GET /events. Assigned customer readers use /audit?organization_id=TENANT_ID or GET /audit/events?organization_id=TENANT_ID. Every page and CSV request rechecks authorization. CSV is a bounded page; continue through the returned cursor to retrieve more history.

A tenant retention-days setting currently records the target policy. It does not schedule expiry. D1 outbox/history is retained until an explicit retention service is configured. Do not assume account deletion or adding a sink satisfies a retention contract.

07 / Adapter boundaries

AdapterPurpose and acknowledgement
D1 captureCommit a business mutation, audit row and outbox together. A failed batch rolls back the transaction.
DynamoDB captureCommit supplied business writes, immutable event and pending outbox in one TransactWriteItems request. Exact retries do not repeat business changes.
PostgreSQL archiveAwait an event insert; exact retries deduplicate, and reused IDs with changed content fail. TLS certificate and hostname checks are required.
SQS deliveryAn accepted send means the queue acknowledged delivery. Consumers must still process and archive the event with persistent deduplication; FIFO deduplication has a limited window.
Tracing mirrorEmit safe diagnostic fields after capture. Subscriber filters and dropped log messages cannot control audit persistence.

The AWS audit adapters and infrastructure template are reusable native components. They do not deploy a complete AWS-hosted Zeroth identity service. The Worker deployment uses D1; AWS applications supply their business writes to the DynamoDB capture adapter. Neither remote PostgreSQL nor SQS shares a transaction with an unrelated application's database.

08 / Connect a Worker stream to a sink

Configure a separate AUDIT_STREAM_TOKEN Worker secret, at least 32 characters. It grants deployment-wide audit-stream access, including platform events. Assign a different consumer ID to each independently populated destination. Keep tokens and database connection strings in environment variables or a secret manager.

# PostgreSQL archive (TLS is required):
ZEROTH_AUDIT_STREAM_URL=https://identity.example.com/audit/stream
AUDIT_STREAM_TOKEN=<deployment stream secret>
AUDIT_CONSUMER_ID=postgres-production
DATABASE_URL=<TLS PostgreSQL connection string>
cargo run -p zeroth-audit-collector --features postgres -- \
  --sink postgres --once

# AWS queue delivery uses the AWS credential provider chain:
AUDIT_SQS_QUEUE_URL=https://sqs.REGION.amazonaws.com/ACCOUNT/audit.fifo
AUDIT_SQS_FIFO_GROUP_ID=audit
cargo run -p zeroth-audit-collector --features aws -- \
  --sink sqs --once

Run schema initialization separately with an owner/migration role using --initialize-schema. The PostgreSQL delivery role should normally have only SELECT and INSERT. Without --once, the collector polls and retries. It acknowledges its source checkpoint only after every event on the page receives the destination's required acknowledgement. Restart or lost acknowledgements replay identical event IDs.

The optional AWS CloudFormation template is deploy/aws/audit.yaml. It defines retained/encrypted storage, an SQS queue and dead-letter queue, and policy examples. Review and deploy it through the normal AWS release process; source code alone creates no cloud resources.

09 / Verify before onboarding

  1. Apply all schema migrations before enabling the new routes. The protected schema-ensure endpoint applies each migration and its version marker atomically.
  2. Test each provider with fresh sign-in, wrong tenant/domain and wrong required-provider cases. Test tenant suspension, policy changes and manual offboarding.
  3. Verify an audit reader cannot view another tenant, platform/legacy history or CSV without export permission.
  4. Inject capture and delivery failures. Check rollback, replay, duplicate handling and the sink's delivery status.
  5. Verify automatic offboarding end to end: unknown managed users denied, inactive records block fresh login, sessions/refresh revoked, stale Directory state denied, and offline enterprise JWTs expire within the configured five-minute window. Agree retention and assurance requirements before promising those controls to customers. The custom reverse proxy remains a later component.
