WAVEY / ZEROTH · SETUP GUIDE

Corporate sign-in & audit delivery

Microsoft Entra, Google Workspace and independent audit adapters.

5 November 2026 · Author: Codex · Ticket: no issue linked

Create a tenant, bind its applications and configure its corporate connection. Audit capture stays local and durable; external destinations are optional.

This guide describes implementation and operator configuration. A saved draft or configured credential is not evidence of a successful live sign-in. Provider credentials can be supplied after the tenant is created.

01 / Tenant setup

  1. Open Tenants in the management UI using a deployment-admin session.
  2. Choose a stable tenant ID and a display name. Select Microsoft Entra or Google Workspace. The initial model has one corporate connection per tenant.
  3. Select existing applications. Binding sets their tenant account namespace and required enterprise provider. Ownership is permanent in this implementation; disable an application instead of moving it between companies.
  4. Add audit readers by their Zeroth user ID. Export permission is separate from read permission. Readers do not gain deployment-admin or user-management rights.
  5. Save the draft. Supply the public provider application ID and credential binding when available. Test a fresh login before onboarding users.

Worker deployments resolve these references through secret bindings. The dedicated TENANT_…_CLIENT_SECRET namespace prevents references to unrelated signing or administrative credentials. A tenant connection never falls back to another tenant's or the deployment's credentials.

Decide whether Entra guest accounts are eligible and configure enterprise-app assignment accordingly. Workspace domain membership alone does not grant an application role. Apply corporate MFA/Conditional Access policy at the upstream provider; SSO alone does not prove MFA.

03 / Users and access

Users appear after sign-in. The current UI supports inspection, tenant filtering, disable/enable and deployment-admin membership changes. It does not offer invitations or directory provisioning. Disabling a user revokes their local sessions and refresh credentials; an offline consumer can still accept an already issued JWT until its expiry.

Tenant bindings govern new identity lookup. Existing unassigned/global accounts are not silently migrated into a corporate tenant. Review account ownership before changing an application's namespace. Audit rows with unknown legacy ownership remain in the deployment operator's history.

04 / Audit history

Administrative writes and critical credential transitions capture an audit record and outbox entry in the database transaction. Audit history survives account deletion as opaque actor/target references. New records use bounded, allowlisted metadata and explicit outcomes; raw tokens, provider error descriptions and credentials do not belong in the event payload.

Deployment admins use the management audit table or GET /events. Assigned customer readers use /audit?organization_id=TENANT_ID or GET /audit/events?organization_id=TENANT_ID. Every page and CSV request rechecks authorization. CSV is a bounded page; continue through the returned cursor to retrieve more history.

A tenant retention-days setting currently records the target policy. It does not schedule expiry. D1 outbox/history is retained until an explicit retention service is configured. Do not assume account deletion or adding a sink satisfies a retention contract.

05 / Adapter boundaries

AdapterPurpose and acknowledgement
D1 captureCommit a business mutation, audit row and outbox together. A failed batch rolls back the transaction.
DynamoDB captureCommit supplied business writes, immutable event and pending outbox in one TransactWriteItems request. Exact retries do not repeat business changes.
PostgreSQL archiveAwait an event insert; exact retries deduplicate, and reused IDs with changed content fail. TLS certificate and hostname checks are required.
SQS deliveryAn accepted send means the queue acknowledged delivery. Consumers must still process and archive the event with persistent deduplication; FIFO deduplication has a limited window.
Tracing mirrorEmit safe diagnostic fields after capture. Subscriber filters and dropped log messages cannot control audit persistence.

The AWS audit adapters and infrastructure template are reusable native components. They do not deploy a complete AWS-hosted Zeroth identity service. The Worker deployment uses D1; AWS applications supply their business writes to the DynamoDB capture adapter. Neither remote PostgreSQL nor SQS shares a transaction with an unrelated application's database.

06 / Connect a Worker stream to a sink

Configure a separate AUDIT_STREAM_TOKEN Worker secret, at least 32 characters. It grants deployment-wide audit-stream access, including platform events. Assign a different consumer ID to each independently populated destination. Keep tokens and database connection strings in environment variables or a secret manager.

# PostgreSQL archive (TLS is required):
ZEROTH_AUDIT_STREAM_URL=https://identity.example.com/audit/stream
AUDIT_STREAM_TOKEN=<deployment stream secret>
AUDIT_CONSUMER_ID=postgres-production
DATABASE_URL=<TLS PostgreSQL connection string>
cargo run -p zeroth-audit-collector --features postgres -- \
  --sink postgres --once

# AWS queue delivery uses the AWS credential provider chain:
AUDIT_SQS_QUEUE_URL=https://sqs.REGION.amazonaws.com/ACCOUNT/audit.fifo
AUDIT_SQS_FIFO_GROUP_ID=audit
cargo run -p zeroth-audit-collector --features aws -- \
  --sink sqs --once

Run schema initialization separately with an owner/migration role using --initialize-schema. The PostgreSQL delivery role should normally have only SELECT and INSERT. Without --once, the collector polls and retries. It acknowledges its source checkpoint only after every event on the page receives the destination's required acknowledgement. Restart or lost acknowledgements replay identical event IDs.

The optional AWS CloudFormation template is deploy/aws/audit.yaml. It defines retained/encrypted storage, an SQS queue and dead-letter queue, and policy examples. Review and deploy it through the normal AWS release process; source code alone creates no cloud resources.

07 / Verify before onboarding

  1. Apply all schema migrations before enabling the new routes. The protected schema-ensure endpoint applies each migration and its version marker atomically.
  2. Test each provider with fresh sign-in, wrong tenant/domain and wrong required-provider cases. Test tenant suspension, policy changes and manual offboarding.
  3. Verify an audit reader cannot view another tenant, platform/legacy history or CSV without export permission.
  4. Inject capture and delivery failures. Check rollback, replay, duplicate handling and the sink's delivery status.
  5. Agree retention, directory provisioning, assurance and offboarding requirements before promising those controls to customers. The custom reverse proxy remains a later component.
