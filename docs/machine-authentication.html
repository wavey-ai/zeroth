Zeroth · implementation guide

Machine authentication

Ticket: not assignedDate: 6 November 2026Author: Codex, for Jamie

A service registers its public keys with Zeroth and obtains short-lived, scoped access tokens over HTTPS. Its private key stays with the service. This authentication protocol works independently of AWS IAM, Azure subscriptions or Google Cloud projects.

The client_credentials grant issues an access token to the service itself. private_key_jwt authenticates that service to the token endpoint using a signed assertion. This follows RFC 6749 §4.4 and RFC 7523.

1. Register the service

Apply the ordinary Zeroth schema migrations, including 0017_service_clients, before enabling the new endpoints. Use an administrator session to open /admin/service-clients. Select an existing tenant and register a service ID beginning with svc_, a display name, allowed API audiences, allowed scopes and a public JWKS. Choose a token lifetime between 60 and 600 seconds.

Service identities have their own registry and do not create human accounts, browser sessions, ID tokens or refresh tokens. Their tenant binding is permanent. Tenant disablement blocks new service-token issuance.

Generate an ES256 key in a secure directory outside the source checkout. The existing key generator produces both the private scalar and public JWKS:

umask 077
zeroth signing-key --kid tier-key-v1 --format json > /secure/tier-key.json
jq '.public_jwks' /secure/tier-key.json

Paste only the public JWKS into the console. Keep the private file in the tier’s secret store. Register one to eight ES256/P-256 public keys with distinct kid values. Private JWK fields, unknown key parameters and unsupported algorithms are rejected.

{
  "id": "svc_beta_runner",
  "tenantId": "beta",
  "name": "Beta release agent",
  "audiences": ["https://control.example.com/releases"],
  "scopes": ["releases:read", "receipts:write"],
  "publicJwks": {"keys": ["REPLACE WITH THE PUBLIC JWK OBJECT"]},
  "disabled": false,
  "tokenTtlSeconds": 600
}

The JSON above illustrates the management fields; replace the key placeholder with the public object emitted by the CLI. Administrators can also use GET /service-clients?tenant_id=beta and POST /service-clients. Browser mutations require the existing same-origin and X-Zeroth-CSRF checks. Updates must include the current expectedRevision.

2. Obtain an access token

Generate a fresh assertion for every HTTP attempt. The CLI reads the private scalar or private JWK from standard input, creates a random assertion identifier and signs a two-minute assertion. It writes the assertion without a trailing newline so curl can read it directly from a file.

jq -r '.jwt_es256_private_key' /secure/tier-key.json |
  zeroth service-assertion \
    --client-id svc_beta_runner \
    --key-id tier-key-v1 \
    --audience https://id.example.com/oauth/token \
  > /secure/assertion.jwt

curl --fail-with-body https://id.example.com/oauth/token \
  --data-urlencode grant_type=client_credentials \
  --data-urlencode client_id=svc_beta_runner \
  --data-urlencode client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer \
  --data-urlencode client_assertion@/secure/assertion.jwt \
  --data-urlencode resource=https://control.example.com/releases \
  --data-urlencode 'scope=releases:read receipts:write'

The assertion’s iss and sub must both equal the service ID. Its aud must exactly match the configured HTTPS token endpoint. Zeroth requires an issued-at time, a short expiry and a unique jti. Assertion identifiers are consumed durably. A concurrent replay can produce only one successful issuance.

resource selects one registered audience. The compatibility field audience is accepted when supplied alone. Supplying both is rejected. Requested scopes must be explicitly granted to the service; human OIDC scopes are reserved.

{
  "access_token": "SIGNED SERVICE ACCESS TOKEN",
  "token_type": "Bearer",
  "expires_in": 600,
  "scope": "releases:read receipts:write"
}

The separate zeroth-machine crate owns assertion construction and signing helpers, service policy types and access-token verification. It depends on portable cryptography and URL libraries, with no OIDC, Worker, storage or cloud adapter dependency. Rust applications import zeroth_machine; the existing zeroth_oidc::service path remains compatible. Applications can keep keys in their own signing system while using the same HTTP protocol.

3. Verify identity at the receiving API

Use verify_service_access_token with trusted issuer keys and explicit expected issuer, tenant, audience, required scopes and current time. Obtain Zeroth’s public keys from its configured JWKS endpoint and maintain a bounded key cache. Select the separate service-token verifier when authorizing machine requests.

ClaimMeaning
sub, client_idThe same registered service identity.
tenant_idThe immutable tenant that owns the service.
aud, scopeThe intended API and explicitly granted operations.
principal_type, token_useservice and access. Human-token verification rejects the service discriminator.
client_revisionThe service policy revision at issuance.
iat, exp, jtiIssue time, bounded expiry and a token identifier.

The receiving API maps the service identity to its own resource permissions. For release management, that means mapping the service to one tier and enforcing access to that tier’s catalog and receipts. Deployment approval and local cloud permissions belong to the release system.

4. Rotate keys and revoke access

  1. Add the new public key alongside the old one using an update with the current revision.
  2. Switch the service to signing assertions with the new key and key ID.
  3. Remove the old public key in another revision-checked update. Old-key assertions will then fail.
  4. Disable the service to block its authentication and new token issuance. The console’s revoke action advances the policy revision while leaving the service enabled.

Every update advances the policy revision. Concurrent stale edits are rejected. Issuance checks the current client and tenant policy in the same database transaction as the replay claim, token record and audit evidence.

Offline verification has a bounded revocation delay. A signed token can remain valid until its expiry, at most ten minutes. APIs requiring a fresher decision must perform an online policy check. Existing tokens never gain new permissions from a subsequent policy expansion.

An enabled service can introspect its own tokens through POST /oauth/introspect, using a fresh client assertion whose audience is the exact introspection endpoint. Include client_id, client_assertion_type, client_assertion and token. Expired, foreign-client or old-revision tokens return active: false. A disabled service cannot authenticate to this endpoint. Cross-client resource-server introspection is outside the current grant model.

5. Cloud boundaries

The identity exchange needs outbound HTTPS and the service’s registered signing key. It requires no cross-account IAM role. The current hosted issuer uses the existing Worker/D1 adapter; the protocol and zeroth-machine verification library carry no cloud IAM requirement.

A tier still needs local permissions for its infrastructure. AWS registry pulls and deployment calls use the AWS adapter’s IAM permissions. Azure and Google adapters use their own registry, secret and deployment credentials. A Zeroth access token is not an ECR login token.

Zeroth supplies identity, scopes and identity audit. The release catalog, signed deployment manifests, durable receipts and tier adoption policy remain separate release-system responsibilities.

6. Validation

The native suite covers assertion signatures, client and audience binding, input bounds, scope grants, tenant binding, human/service token separation and SQL transaction guards. The local Worker/D1 acceptance harness exercises real HTTP registration, issuance, concurrent replay, rotation, disablement, restart persistence and audit redaction:

cargo test --workspace --all-targets --locked
cargo check -p zeroth-worker --target wasm32-unknown-unknown --locked
node crates/zeroth-worker/test/machine-http-integration.mjs

The HTTP harness uses synthetic keys and a private temporary D1 database. It requires the same local worker-build, wasm-bindgen and Wrangler tools as test/local-http-integration.mjs. It contacts no Cloudflare account or live tenant.
